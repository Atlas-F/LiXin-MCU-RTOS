# 内存段持久化与运行时资源风险分析

## 1. 结论

当前工程把 `Bsp_Led_Handler_t` 和 `BspLedDriver_t` 放入自定义 `bsp_target` 段，并尝试将运行后的内存内容导出到 HEX，使后续启动能够跳过部分实例化过程。

这个思路只适合持久化“纯数据配置”，不适合直接持久化完整的 Handler/Driver 运行时对象。原因是对象中同时包含：

- 函数指针；
- 接口表指针；
- FreeRTOS 队列句柄；
- FreeRTOS 任务句柄；
- 指向其他 RAM 对象的指针；
- 与当前固件链接布局和 RTOS 运行时状态有关的地址。

因此，固定内存段只能固定对象本身的位置，不能保证对象引用的资源在下一次启动或下一版固件中仍然有效。

推荐的原则是：

> 持久化配置，不持久化运行时对象图；每次启动恢复数据，但重新绑定函数指针、重新创建 RTOS 资源。

---

## 2. 当前工程的实现

工程目录：`21_LED_Driver_BridgeMode`。

在 [`System_adaption.c`](21_LED_Driver_BridgeMode/System/System_adaption.c) 中，两个对象被放入 `bsp_target` 段：

```c
__attribute__((used, section("bsp_target")))
static Bsp_Led_Handler_t bsp_led_handler_instance = {0};

__attribute__((used, section("bsp_target")))
static BspLedDriver_t led_1 = {0};
```

Scatter 文件 [`21_LED_Driver_BridgeMode_MyCustom.sct`](21_LED_Driver_BridgeMode/MDK-ARM/21_LED_Driver_BridgeMode/21_LED_Driver_BridgeMode_MyCustom.sct) 将该段配置为：

```text
Load Address:      0x08007000
Execution Address: 0x20019000
```

含义是：

```text
Flash/HEX 中保存初始化镜像：0x08007000
启动后运行对象所在的 SRAM：0x20019000
```

这是一份 Flash 到 RAM 的初始化镜像，不是对 SRAM 运行时状态的天然持久化。

当前 map 文件显示：

```text
bsp_led_handler_instance -> 0x20019000
led_1                    -> 0x20019034
```

## 3. 为什么函数指针会失效

`BspLedDriver_t` 中包含：

```c
BspLedOperations_t   *operations;
BspLedTimeBaseMs_t   *time_base_ms;
BspLedOsDelay_t      *os_delay;
BspLedDriverControl_t BspLedDriver_Control;
```

`Bsp_Led_Handler_t` 中包含：

```c
time_base_ms;
os_delay;
os_queue;
os_thread;
critical_region;
Bsp_Led_Handler_Control;
Bsp_Led_Handler_RegisterDriver;
```

这些字段最终保存的只是地址。例如：

```text
BspLedDemo_On           = 0x0800xxxx
BspLedDemo_QueuePop     = 0x0800xxxx
Bsp_Led_Handler_Control = 0x0800xxxx
```

函数地址会受到以下因素影响：

- 增删函数或改变函数顺序；
- 编译器优化等级；
- LTO 开关；
- `printf` 或其他库函数变化；
- 链接脚本变化；
- 结构体和全局变量变化；
- 固件升级后的代码布局变化。

例如旧版本中：

```text
BspLedDemo_On = 0x08000465
```

新版本中该函数可能变为：

```text
BspLedDemo_On = 0x08000610
```

如果仍使用旧对象中的 `0x08000465`，CPU 不会知道该地址原本属于哪个符号，而是直接跳转。结果可能是：

1. 跳入其他函数；
2. 跳入普通数据；
3. 跳入无效区域并触发 HardFault；
4. 因 Thumb 位、参数或调用约定错误导致栈破坏；
5. 系统表面运行，但行为已经错误。

HEX 只保存地址和值，不保存 C 符号名，也不保存可供运行时重新定位的重定位信息。

## 4. 比函数指针更危险的运行时资源

### 4.1 FreeRTOS 队列句柄

Handler 实例化时通过适配层调用 `xQueueGenericCreate()`，随后把返回值保存到 `queue_handle`。

这个句柄指向当前这次启动创建的 FreeRTOS 队列对象。重启后：

- FreeRTOS 内核重新初始化；
- heap 重新初始化；
- 原队列对象不存在；
- 旧句柄只是一个可能已经失效的地址。

### 4.2 FreeRTOS 任务句柄

Handler 通过 `xTaskCreate()` 创建线程，并保存 `thread_handle`。任务控制块、任务栈、调度器链表均属于本次启动的运行时状态，不能从上一次启动直接恢复。

### 4.3 `instance_group` 指针

Handler 内部有静态对象：

```c
static BspLedHandlerInstanceGroup_t instance_group = {0};
handler_self->instance_group = &instance_group;
```

持久化后保存的只是该静态对象的地址。它依赖 `.bss` 布局、链接顺序、结构体大小和其他全局对象，不能把地址本身当成持久化资源。

### 4.4 接口表指针

`operations`、`os_queue`、`os_thread` 等通常指向适配层中的静态接口表。这些接口表本身也可能因编译布局变化而改变地址，因此不能只保存它们的指针。

## 5. 当前工程中跳过初始化的风险点

Driver 实例化会绑定：

```c
self->operations   = operations;
self->os_delay     = os_delay;
self->time_base_ms = time_base_ms;
self->BspLedDriver_Control = BspLedDriver_Control;
```

Handler 实例化会绑定：

```c
handler_self->time_base_ms = time_base_ms;
handler_self->os_delay     = os_delay;
handler_self->os_queue     = os_queue;
handler_self->os_thread    = os_thread;

handler_self->Bsp_Led_Handler_Control = Bsp_Led_Handler_Control;
handler_self->Bsp_Led_Handler_RegisterDriver = Bsp_Led_Handler_Register;
```

此外还会：

```text
创建 instance_group
创建 Queue
创建 Handler 线程
注册 led_1
```

如果仅依靠持久化数据把 `initialized` 标记为已初始化，然后跳过这些步骤，就等于同时跳过了：

- 本次启动的函数指针绑定；
- 本次启动的接口表绑定；
- 本次启动的队列创建；
- 本次启动的任务创建；
- 本次启动的设备注册。

例如下面的调用链就可能使用失效资源：

```c
handler_self->os_queue->Bsp_Led_Handler_PopQueue(
    handler_self->queue_handle,
    &led_event,
    portMAX_DELAY);
```

这里同时依赖 `os_queue` 和 `queue_handle` 两个运行时对象。任意一个失效，都可能导致异常；两个都来自旧启动状态时，风险更高。

## 6. 哪些数据可以持久化

适合持久化的内容是与地址无关的纯数据：

```text
cycle_time_ms
blink_times
proportion_on_off
led_index
设备配置
校准结果
用户设置
状态计数
版本号
```

不应直接持久化的内容是运行时资源：

```text
普通对象指针
函数指针
QueueHandle_t
TaskHandle_t
MutexHandle_t
SemaphoreHandle_t
FreeRTOS 内核对象地址
动态内存地址
链表节点指针
HAL 外设句柄中的运行时地址
```

可以保存逻辑标识：

```text
driver_id = 0
os_backend = FREERTOS
led_index = LED_INDEX_1
```

但不要保存对应的绝对地址：

```text
operations = 0x20000094
BspLed_On = 0x08000465
queue_handle = 0x20001234
```

## 7. 推荐的数据与运行时对象分离方式

### 7.1 持久化数据结构

```c
typedef struct
{
    uint32_t magic;
    uint16_t version;
    uint16_t size;
    uint32_t crc;

    uint32_t cycle_time_ms;
    uint32_t blink_times;
    uint32_t proportion_on_off;
    uint32_t led_index;
} LedPersistentData_t;
```

这里保存的是配置和校验信息，不包含任何指针。

### 7.2 运行时上下文

```c
typedef struct
{
    LedPersistentData_t persistent;

    BspLedOperations_t *operations;
    BspLedTimeBaseMs_t *time_base_ms;
    BspLedOsDelay_t *os_delay;

    QueueHandle_t queue_handle;
    TaskHandle_t thread_handle;

    uint8_t runtime_bound;
} LedRuntimeContext_t;
```

启动时重新生成或绑定其中的运行时字段。

## 8. 推荐启动流程

```text
1. 从 Flash/指定内存段读取持久化配置
2. 检查 magic、version、size、CRC
3. 配置有效：加载配置；配置无效：使用默认值
4. 每次启动重新绑定函数指针和接口表
5. 每次启动重新创建 Queue、Task、Mutex 等 RTOS 资源
6. 重新实例化或注册 Driver/Handler
7. 将持久化配置复制到运行时对象
8. runtime_bound = true
9. 允许业务层发送控制命令
```

可以跳过的是：

```text
硬件校准
设备扫描
固定的长时间稳定等待
已经验证有效的配置解析
```

不应跳过的是：

```text
函数指针绑定
接口表绑定
FreeRTOS 对象创建
任务创建
设备注册
运行时一致性检查
```

## 9. 关于当前 600 ms 延时的优化

当前 [`BSP_Led_Driver.c`](21_LED_Driver_BridgeMode/BSP/LED/Driver/Src/BSP_Led_Driver.c) 的初始化流程包含：

```c
self->operations->BspLed_Off();
self->os_delay->BspLed_DelayMs(600U);
self->time_base_ms->BspLed_GetTimeMs(&time_stamp);
```

如果优化目标只是减少这段硬件稳定等待，不应跳过整个 Handler/Driver 实例化。更合理的拆分是：

```text
软件对象绑定：每次启动执行
RTOS 队列/任务创建：每次启动执行
LED 初始硬件等待：按持久化状态决定是否跳过
设备校准：根据版本和 CRC 决定是否跳过
```

这样可以获得启动加速，同时不破坏运行时资源的有效性。

## 10. 必须具备的失效检测与恢复

持久化结构至少应包含：

```text
magic
schema_version
struct_size
crc
```

启动时检查：

```text
magic 是否正确
版本是否兼容
结构体大小是否匹配
CRC 是否正确
枚举值和数值范围是否合法
```

需要特别注意：

> CRC 只能证明数据没有被破坏，不能证明其中保存的函数指针仍属于当前固件。

因此，即使 CRC 正确，也必须重新绑定函数指针和重新创建 RTOS 资源。

如果系统必须兼容不同固件版本，还可以增加：

```text
firmware_version
layout_id
configuration_schema_version
```

但最稳妥的办法仍然是不保存地址型运行时数据。

---

## 11. 最终设计原则

该方案应从：

```text
保存完整实例，跳过初始化
```

调整为：

```text
保存配置和可验证状态
启动时重新建立运行时对象
只跳过确实可以跳过的硬件耗时步骤
```

一句话概括：

> 内存段持久化适合保存“状态”，不适合保存“运行时关系”；函数、指针、队列、任务和内核对象必须在本次启动中重新建立。
